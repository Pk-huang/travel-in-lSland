Data 規劃測試的內容

測試結果記錄格式：
- 測試結果：成功 / 失敗
- 失敗項目：無 / 連線測試 / 回應狀態測試 / fallback 測試 / 資料契約驗證
- 備註：

1. Source / API / JSON

   功能與測試內容：

   - API 是否能正常連線並下載，並具備可靠的備用資料來源

     資料來源：

      A. 主資料源

        - NOAA SWPC Aurora JSON
          用途：極光預報
          格式：JSON API
          目前狀態：來源存在，尚未接入程式
          優先級：高

        - Vedur Weather API
          用途：冰島天氣、測站、觀測資料
          格式：JSON API
          目前狀態：已接入程式並使用
          優先級：高


      B. 備用資料源

        - APIs.is
          用途：公開資料彙整入口
          格式：JSON API
          目前狀態：來源存在，尚未接入程式
          優先級：中

        - 本地 snapshot fixture
          用途：API 失敗時提供保底資料
          格式：本地 JSON
          目前狀態：已接入程式並使用
          優先級：高（保底）

        - Umferdin 網頁資料
          用途：冰島道路資訊參考
          格式：網站資料，尚未確認為穩定 JSON API
          目前狀態：來源存在，尚未接入程式
          優先級：低


      C. 參考資料源

        - Vedur 北極光頁面
          用途：人工比對與情境驗證
          格式：HTML 網頁
          目前狀態：僅供人工參考，未接入程式
          不作正式 API
          優先級：低


      D. 目前程式已使用但原清單未完整列出的資料源

        - Sunrise-Sunset API
          用途：日出、日落與日照資料
          格式：JSON API
          目前狀態：已接入程式並使用
          優先級：中

     測試內容： 驗證主資料源可用性，確認失敗時是否可切換至備用資料來源。

     1. 連線測試
        - 驗證：確認 API 是否可正常連線，並成功取得 JSON。
          執行方式：自動化腳本請求主資料源與備用資料源，檢查 HTTP 狀態與 JSON 是否可解析。
          測試檔案：src/lib/api/api-connect.test.tsx
          成功條件：HTTP 200 / JSON parse 成功
          參與檔案：src/lib/api/api-connect.test.tsx、src/lib/api/vedur.ts、src/lib/api/sun-times.ts、src/lib/http/client.ts
          結果：失敗
          失敗項目：連線測試
          備註：
          - NOAA SWPC Aurora JSON -- 失敗：測試環境連線 timeout
          - Vedur observations -- 成功
          - Vedur stations -- 成功
          - APIs.is -- 失敗：測試環境連線失敗
          - Sunrise-Sunset API -- 成功
          - 本地 snapshot fixture -- 成功

        - 驗證：確認主資料源是否成功回應資料。
          執行方式：自動化腳本呼叫主資料源，檢查是否回傳成功狀態與有效資料。
          測試檔案：src/lib/api/api-connect.test.tsx
          成功條件：主資料源回應 HTTP 200，JSON parse 成功，且 Vedur function 回傳資料。
          參與檔案：src/lib/api/vedur.ts、src/app/data/iceland-status/route.ts
          結果：失敗
          備註：Vedur observations 與 Vedur stations 成功；NOAA SWPC Aurora JSON 因測試環境連線 timeout 失敗。

        - 驗證：確認備用資料源與 fallback 資料是否可用。
          執行方式：自動化腳本驗證備用資料源與 local fixture 是否能正常回應並被選用。
          測試檔案：src/lib/api/api-connect.test.tsx
          成功條件：備用資料源回應 HTTP 200 且 JSON parse 成功；本地 snapshot fixture 可正常讀取。
          參與檔案：src/app/data/iceland-status/route.ts、src/lib/http/circuit-breaker.ts
          結果：失敗
          備註：本地 snapshot fixture 成功；APIs.is 因測試環境連線失敗，且本次尚未驗證 fallback 是否被選用。

    - 設定優先順序與載入順序

     功能目的：確認系統依照優先順序選擇正確資料來源，並在初始化前完成載入。

     測試內容：檢查資料優先順序是否正確，載入時機是否在 render pipeline 啟動前完成。
              
        - 驗證：模擬主 JSON 與次來源同時可用，驗證最終採用主 JSON。
          執行方式：於 route 測試中同時 mock 主來源與次來源皆回傳成功 JSON，檢查回應 payload 的來源標記與資料內容是否來自主來源。
          測試檔案：src/app/data/iceland-status/route.test.ts
          成功條件：回應為 HTTP 200；meta.fallback = false；資料內容符合主來源 mock，未被次來源覆蓋。
          參與檔案：src/app/data/iceland-status/route.ts、src/lib/http/client.ts
          結果：成功
          備註：已於 src/app/data/iceland-status/json-priority-loading.integration.test.ts case「主次來源同時可用時採用主 JSON」驗證通過；確認回應 HTTP 200、meta.fallback = false，且資料未落入 snapshot fallback。

        - 驗證：模擬主來源失敗、fallback JSON 可用，驗證最終採用 fallback JSON。
          執行方式：於 route 測試中 mock 主來源拋錯（timeout 或 5xx），並提供本地 snapshot fixture 或備援來源成功 JSON，確認流程切換至 fallback。
          測試檔案：src/app/data/iceland-status/route.test.ts
          成功條件：回應為 HTTP 200；meta.fallback = true；回應資料可通過 schema parse，且內容符合 fallback JSON。
          參與檔案：src/app/data/iceland-status/route.ts、src/lib/http/circuit-breaker.ts、src/schemas/domain.ts
          結果：成功
          備註：已於 src/app/data/iceland-status/json-priority-loading.integration.test.ts case「主來源失敗時切換到 fallback JSON」驗證通過；mock 主來源 503 後仍回應 HTTP 200、meta.fallback = true，且資料可通過 schema parse。

        - 驗證：在前端狀態層測試載入流程，驗證 render-ready 訊號出現前不觸發地圖資料消費。
          執行方式：於 hook 測試中模擬 API 延遲回應，先驗證 loading 狀態期間不輸出可渲染資料，再驗證資料到齊後才進入可渲染狀態。
          測試檔案：src/lib/client/use-iceland-status.test.tsx
          成功條件：loading 階段不產生 render-ready 資料；資料載入完成後才輸出可迭代集合與必要欄位；過程無未捕捉例外。
          參與檔案：src/lib/client/use-iceland-status.ts、src/lib/adapters/weather.ts、src/lib/adapters/road.ts
          結果：成功
          備註：已於 src/app/data/iceland-status/json-priority-loading.integration.test.ts case「render-ready 前不輸出可渲染資料」驗證通過；先觀察 loading=true 且 data=null，待 fetch resolve 後才進入 loading=false 並輸出資料。

        - 驗證：連續執行多次（例如 20 次）檢查採用來源與 ready 時序。
          執行方式：針對上述三個案例以同一組 mock 條件重複執行 20 次，統計每次來源選用結果與狀態轉換順序。
          測試檔案：src/app/data/iceland-status/route.test.ts、src/lib/client/use-iceland-status.test.tsx
          成功條件：20 次結果一致；來源優先順序不漂移；每次皆先完成資料 ready 再進入可渲染狀態。
          參與檔案：src/app/data/iceland-status/route.ts、src/lib/client/use-iceland-status.ts
          結果：成功
          備註：已於 src/app/data/iceland-status/json-priority-loading.integration.test.ts case「連續 20 次執行來源優先與 ready 時序皆一致」驗證通過；20 次皆維持主來源優先與正確載入時序，無失敗樣本。

     驗證條件：正確資料被優先選擇，且在地圖渲染前已準備完成。


     

   - API 內容是否已轉換成 render 所需的 data

     功能目的：確認原始資料已轉換成後續流程可直接使用的資料結構。

     測試內容：僅做 Smoke 驗證，確認資料可流到轉換層且 repo 已有可用 JSON；不在此驗證轉換細節。

        - 驗證：資料可流到轉換層（Smoke）。
          執行方式：以最小 API/JSON 樣本呼叫 route，確認可進入 adapter/schema 轉換流程（可用 mock 或 spy 驗證入口被執行）。
          測試檔案：src/app/data/iceland-status/route.test.ts
          成功條件：回應為 HTTP 200 或受控 fallback；且轉換層入口有被執行。
          參與檔案：src/app/data/iceland-status/route.ts、src/lib/adapters/weather.ts、src/schemas/domain.ts
          結果：成功
          備註：已於 src/app/data/iceland-status/route.test.ts case「資料可流到轉換層（Smoke）」驗證通過；確認回應 HTTP 200、parseWeather 已被呼叫且回應可通過 schema parse。轉換正確性與欄位完整性由「Data transformation layer > Transform / data conversion」驗證，不在此重複測試。


        - 驗證：資料是否可直接進入 render pipeline。
          執行方式：自動化腳本驗證資料結構是否符合 map / canvas 所需解構。
          測試檔案：src/lib/adapters/weather.test.ts、src/lib/adapters/stations.test.ts、src/lib/adapters/road.test.ts、src/lib/client/use-iceland-status.test.tsx
          成功條件：adapter 輸出結構可直接被前端狀態層消費（weather/roads 為可迭代陣列、必要座標與時間欄位可用），渲染流程不需額外轉型。
          參與檔案：src/lib/adapters/weather.ts、src/lib/adapters/stations.ts、src/lib/adapters/road.ts
          結果：成功
          備註：weather.test.ts 7 個 structure case、road.test.ts 7 個 structure case、stations.test.ts 7 個 lookup table case 全過；已驗證 array 迭代、必要欄位型別、座標與時間戳可用。

     
     
     驗證條件：已確認資料可進入轉換層，且轉換細節驗證責任已明確下放至 Transform 層。

  

2. Validation / schema / fallback

   工作：驗證資料是否完整、格式正確，並在失敗時提供回復機制。

   內容：檢查資料契約、資料完整性、缺失欄位處理與 fallback 策略。

   功能與測試內容：

   1. 資料來源與資料完整性驗證
      - 驗證：確認 API 回應是否為成功狀態（200 / 正確 JSON）。
        執行方式：使用 unit test mock fetch 回傳 HTTP 200 與有效 JSON，直接呼叫 fetchJson，驗證函式成功解析並回傳資料。
        測試檔案：src/lib/http/client.test.ts
        成功條件：HTTP 200 時，fetchJson 成功完成並回傳解析後的 JSON。
        參與檔案：src/lib/http/client.ts、src/lib/http/client.test.ts
        結果：成功
        失敗項目：無
        備註：測試不依賴外部網路，未額外驗證 Content-Type、schema 或 fallback。

      - 驗證：主 API 成功時使用主資料。
        執行方式：自動化腳本模擬主資料源可用，確認系統選擇主資料來源。
        測試檔案：src/app/data/iceland-status/route.test.ts
        成功條件：上游請求成功時，回應為 HTTP 200，meta.fallback = false，且資料內容來自即時上游（非 snapshot fixture）。
        參與檔案：src/app/data/iceland-status/route.ts
        結果：成功
        備註：對應 route.test.ts case「主 API 成功時使用主資料」通過。

      - 缺口與補測規劃：外部來源穩定性證據不足（受測試環境 timeout 影響）。
        現況缺口：NOAA SWPC 與 APIs.is 在測試環境出現連線 timeout，現有結果不足以證明來源穩定可用。
        補測方式：同一來源連續請求 20 次，分 3 個時段（早/中/晚）各執行 1 輪，記錄 HTTP 狀態、timeout、平均延遲與 JSON parse 成功率。
        測試檔案：src/lib/api/api-connect.test.tsx（新增穩定性測試案例）
        成功條件：每一來源整體成功率 >= 95%，且任一時段成功率 >= 90%；timeout 比例 <= 10%。
        結果：部分已驗證
        備註：本次 20 次連續探測結果為 NOAA 20/20（100%）、APIs.is 0/20（0%）；另在 vitest 單次執行中 NOAA 與 APIs.is 仍出現 timeout，顯示測試環境路徑與直連探測結果存在差異。若未達門檻，需補上 fallback 選用證據與失敗分類統計（DNS / TCP / timeout / 5xx）。

   2. JSON 資料格式是否完整
      - 驗證：必要欄位是否存在。
        執行方式：自動化腳本檢查資料 schema 的必填欄位是否全部存在。
        測試檔案：src/schemas/domain.test.ts、src/app/data/iceland-status/route.test.ts
        成功條件：缺少必填欄位（meta、weather、roads、aurora、summary）時，schema 驗證失敗；欄位齊全時可成功 parse。
        參與檔案：src/schemas/domain.ts
        結果：成功
        備註：domain.test.ts case「icelandStatusResponseSchema - required fields」全 5 個通過。

      - 驗證：欄位型別是否正確。
        執行方式：自動化腳本檢查欄位型別是否符合預期格式。
        測試檔案：src/schemas/domain.test.ts、src/lib/adapters/weather.test.ts
        成功條件：型別正確資料可通過 zod schema；錯誤型別（例如字串溫度、無效 datetime）必定被拒絕並回傳可識別驗證錯誤。
        參與檔案：src/schemas/domain.ts、src/lib/adapters/weather.ts
        結果：成功
        備註：domain.test.ts「icelandStatusResponseSchema - field types」6 個 type validation case 全過；weather.test.ts deriveAlertLevel 邏輯驗證 9 個 case 全過。

   3. 地理資料與數值範圍驗證
      - 驗證：缺失欄位時是否可進行 default / fallback（含座標欄位）。
        執行方式：自動化腳本刪除欄位或設為空值，確認 fallback 邏輯是否生效。
        測試檔案：src/app/data/iceland-status/route.test.ts、src/schemas/domain.test.ts、src/lib/adapters/weather.test.ts
        成功條件：缺值時可套用既定 default（例如數值欄位補 0 或 optional 欄位省略），若仍不合法則進入受控 fallback/錯誤回應，不產生未處理例外。
        參與檔案：src/app/data/iceland-status/route.ts、src/schemas/domain.ts
        結果：成功
        備註：weather.test.ts「parseWeather - default/fallback for missing fields」5 個 case、road.test.ts 3 個座標 fallback case、route.test.ts 1 個空資料 case 全過；已驗證溫度/風速/座標补 0、降水留 undefined、邊界情況不崩潰。

      - 驗證：資料是否可直接進入 render pipeline（含必要座標與時間欄位可用）。
        執行方式：自動化腳本驗證資料結構是否符合 map / canvas 所需解構。
        測試檔案：src/lib/adapters/weather.test.ts、src/lib/adapters/stations.test.ts、src/lib/adapters/road.test.ts、src/lib/client/use-iceland-status.test.tsx
        成功條件：adapter 輸出結構可直接被前端狀態層消費（weather/roads 為可迭代陣列、必要座標與時間欄位可用），渲染流程不需額外轉型。
        參與檔案：src/lib/adapters/weather.ts、src/lib/adapters/stations.ts、src/lib/adapters/road.ts
        結果：成功
        備註：weather.test.ts 7 個 structure case、road.test.ts 7 個 structure case、stations.test.ts 7 個 lookup table case 全過；已驗證 array 迭代、必要欄位型別、座標與時間戳可用。

      - 缺口與補測規劃：合理範圍規則尚未明確驗證。
        現況缺口：目前以結構/型別與部分 fallback 為主，缺少經緯度上下限、高度區間與極端值邊界測試。
        補測方式：在 adapter/schema 測試新增邊界資料集，覆蓋合法邊界值、越界值與極端值（NaN/Infinity/超大值）。
        測試檔案：src/lib/adapters/road.test.ts、src/lib/adapters/stations.test.ts、src/schemas/domain.test.ts
        成功條件：
        - 經度限制在 [-180, 180]、緯度限制在 [-90, 90]。
        - 高度值限制在設定區間（先以 DEM 實測 min/max 定義）。
        - 越界與無效值必須被拒絕、修正或進入受控 fallback，且不產生未處理例外。
        結果：部分已驗證
        備註：既有相關測試已通過 36/36（src/lib/adapters/road.test.ts、src/lib/adapters/stations.test.ts、src/schemas/domain.test.ts），目前可證明結構與 fallback 流程正常；但經緯度上下限、高度區間與極端值邊界規則仍需新增明確測試 case。

   4. 異常資料處理
      - 驗證：確認 timeout、403、500、空回應時的處理方式。
        執行方式：使用 unit test mock fetch 模擬 timeout、403、500 與空回應，直接呼叫 fetchJson，驗證錯誤是否統一轉換為 UpstreamError。
        測試檔案：src/lib/http/client.test.ts
        成功條件：timeout 與空回應轉換為 UpstreamError；403 與 500 的 UpstreamError 保留對應 HTTP status；錯誤情境不回傳未處理例外。
        參與檔案：src/lib/http/client.ts、src/lib/http/client.test.ts
        結果：成功
        失敗項目：無
        備註：共 4 類錯誤情境測試通過；本項只驗證 HTTP client 的錯誤處理，不驗證 fallback 選用或 circuit breaker 狀態轉換。

      - 驗證：主 API 失敗時切換至備用資料。
        執行方式：自動化腳本 mock 主資料源失敗，驗證是否轉向備用資料源。
        測試檔案：src/app/data/iceland-status/route.test.ts、src/lib/http/circuit-breaker.test.ts
        成功條件：主資料源失敗時，系統不回傳未處理例外；可回應 fallback 資料（stale cache 或 snapshot），且 meta.fallback = true。
        參與檔案：src/app/data/iceland-status/route.ts、src/lib/http/circuit-breaker.ts
        結果：成功
        備註：對應 route.test.ts case「主 API 失敗時切換至 fallback 路徑」通過；本次未新增 circuit-breaker 單測。
